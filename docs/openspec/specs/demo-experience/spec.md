# demo-experience Specification

## Purpose
规定上游与两个外部平台 Mock、客户消息中心和中台运维页面的演示行为，使完整链路可以由实际接收事实验收，而不把中台任务状态当作外部已收到，也不依赖真实平台身份体系或额外业务去重能力。

## Requirements

### Requirement: 四个独立控制台提供明确操作路径
系统 MUST 保留中台、上游、平台A和平台B的独立页面地址，各页采用统一浅色控制台视觉和本平台独立导航；侧栏即使在窄窗口 MUST 显示文字名称，导航选中和刷新恢复正确。跨平台入口 MUST 明确打开独立页面。中台 MUST 提供配置的Grafana看板新标签跳转，不将该链接视为身份切换。

#### Scenario: 独立页面与跨平台核查
- **WHEN** 用户在上游完成提交并查看链路，再到平台核对实际实收
- **THEN** 原提交记录保留，各页菜单对应自己的视图；中台与平台事实来自各自接口，页面不展示原型固定数值

#### Scenario: 受保护操作与不明结果
- **WHEN** 绑定、故障控制或人工命令需要本地令牌，或者响应不明
- **THEN** 页面提供清晰的输入、步骤、等待和错误反馈，不静默跳过鉴权、不自动重交，并保留原标识核查路径

### Requirement: 上游生成唯一成交且不自动重交不确定请求
上游Mock MUST 为每条正常成交生成唯一msgId，支持单条及有界可调负载；对已发送后响应超时/丢失的请求只查询msgId或标记人工核查，不自动重新提交。仅明确处理前拒绝可以退避再次提交。

#### Scenario: 响应丢失和查询暂空
- **WHEN** 成交已发出但响应不明，随后查询暂不可用
- **THEN** 上游显示未确认/待核查，不把查询暂空当成再次发送许可

### Requirement: Mock独立保存本平台实际收到的通知
平台1 MUST 保存合法八字段后才返回约定成功；平台2 MUST 实际消费并保存通知后推进连续位点，按topic/partition/offset处理同条记录重放，不新增跨尝试业务去重。两平台存储身份 MUST 隔离。

#### Scenario: 两平台UID分别可见
- **WHEN** 同一客户在两平台绑定不同UID并提交合法成交
- **THEN** 两边实际接收记录分别使用本平台UID、字段和时间精度，不读取中台任务表生成接收记录

### Requirement: 客户消息中心与中台运维分别使用权威数据源
两个客户消息中心 MUST 只查询各自Mock的实际接收记录，支持UID/traceId查询和有界刷新；中台运维入口 MUST 独立查询MySQL状态/失败/尝试及人工命令结果。页面不得把Broker成功改写成已消费或主动触发投递。

#### Scenario: 暂停平台2消费
- **WHEN** Broker已确认但平台2消费暂停，随后恢复
- **THEN** 中台可显示交付成功，平台2客户页面暂停期间无新增，实际消费后才出现；A不受此展示延迟影响

### Requirement: 绑定及故障演示保持明确生效边界
平台Mock MUST 支持固定平台身份的简单绑定/解绑Kafka事件操作，并以权威关系确认消费生效；故障入口支持A处理前拒绝/保存后超时以及B暂停消费。演示接口 MUST 限本机/同源、使用本地令牌及负载上限，不伪装真实身份核验。

#### Scenario: 解绑生效后仅影响新成交
- **WHEN** 页面发出解绑操作且权威查询确认已生效，再提交新的唯一成交
- **THEN** 新成交不再为该平台创建目标，页面操作发出到消费生效之间明确显示等待状态，原在途任务仍按固定UID处理

### Requirement: 待处理与人工恢复提供明确对象及命令状态

投递列表 MUST 分别展示投递任务编号 deliveryId、所属消息编号 msgId、中文平台和状态；路由列表仅展示消息编号。一个消息可对应多个平台投递任务。人工区按任务信息、操作人及修复原因、操作结果排列，按钮不承载长标识。恢复成功只表示新周期已保存，提供只读的消息链路进度入口；原始命令与响应折叠展示。

页面 MUST 仅在结果未确认时显示“确认上次提交”，明确使用原 operationId 与原参数重新 POST，可能完成首次未保存的命令，并非只读查询。未确认期间锁定输入与新操作，切换查询不能替换原目标。确定性拒绝不提供盲重试，成功后旧快照操作保持禁用。保留原任务、固定 UID、尝试历史及后端接口语义；正式演示只做只读验证，保留卷滚动更新两实例。

#### Scenario: 区分消息与平台投递任务
- **WHEN** 用户查询待处理并选择一个投递或路由对象
- **THEN** 投递显示deliveryId及所属msgId，路由仅显示msgId；选择不提交命令，人工区按对象、修复说明、结果排列，按钮不承载长标识

#### Scenario: 恢复申请保存后查询实际进度
- **WHEN** 恢复接口确认保存匹配operationId和目标的新周期
- **THEN** 显示周期及操作摘要且提示不代表投递成功，原始响应折叠，“查看恢复进度”只GET原消息链路

#### Scenario: 未确认命令沿原参数重新提交
- **WHEN** 提交超时、服务不可用或响应与申请不符
- **THEN** 锁定原目标与参数，仅显示“确认上次提交”，明确重新POST原operationId及完全相同序列化参数，不能生成新申请或被其他查询替换目标

#### Scenario: 旧快照与迟到响应不得重新启用恢复
- **WHEN** 已提交对象保存成功或被确定性拒绝，用户重新选择旧行，或提交前与期间发起的查询迟到返回
- **THEN** 恢复按钮保持禁用并提示刷新，只有操作结束后发起的新权威查询才能重新判断是否允许恢复

### Requirement: 上下游演示页提供清晰标识、完整字段和可辨识状态
上游测试记录 MUST 分列显示msgId与traceId，提交确认 MUST 使用中文状态标签，区分首轮完成、已保存接管、未确认、拒绝和明确未发送，保留HTTP及原始状态供核查，不能把外层HTTP成功或首轮完成视为外部已实收。A/B接收卡片 MUST 保留双列业务字段，采用中文标签、次级协议字段名、独立值区域；完整覆盖各自八字段协议、标明接收元数据，缺失值不得补造，未知字段和值安全保留。B消费状态 MUST 通过醒目状态卡区分尚未读取、读取/提交中、运行中、已暂停与未确认；请求进行时不展示旧确认状态，失败不保留绿色运行结论，状态不能代替实际落库。

#### Scenario: 上游提交记录按标识和确认语义展示
- **WHEN** 成交提交成功、拒绝、未发送或响应不明
- **THEN** 两个标识分别可读，确认标签为中文并保留原始事实，查询仅GET、不重新提交成交

#### Scenario: 双平台字段完整且层级清楚
- **WHEN** 查询A或B实际接收记录
- **THEN** 卡片逐字段显示协议八字段和接收元数据，中文名、原名和值层级可辨，长标识安全换行，未知/缺失/零值不被丢弃或改写

#### Scenario: 消费状态确认与未确认清晰区分
- **WHEN** 读取或控制B消费者状态，或者响应失败/格式无效
- **THEN** 展示对应醒目状态，明确Broker确认和消费入库边界，结果不明时禁用控制并要求重新读取，不自动重发
