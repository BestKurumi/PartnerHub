# 架构与业务边界

中台接收唯一msgId的成交原始输入，校验后查询客户在平台A／B的权威绑定。每条消息固定路由与目标UID，后续解绑或新绑定不修改历史目标，不补发旧NO_ROUTE消息。

- MySQL：权威绑定、成交归档、投递尝试、恢复责任、人工操作历史；平台A／B使用各自独立schema和账号保存实收。
- Redis：绑定短缓存、完整快照暂存及归档队列；AOF和noeviction是启动条件，未归档快照无TTL。归档重放仅写审计，不触发外发。
- Kafka：`customer.binding.events`是绑定输入，`platform2.trade.notifications`是平台B输出；不使用Kafka成交输入Topic。
- 平台A：HTTP确认，持久保存后响应；断连或超时可能已经收到，UNKNOWN不能解释为未发送。
- 平台B：Broker确认和消费者实际入库分别核查；按来源位点防止消费重放，不承诺跨新尝试恰好一次。
- 双中台：共享持久责任，每实例独立额度；有限自动恢复后进入待人工处理，人工操作保留operationId及原任务历史。
- 查询：只读MySQL事实，不会触发重新投递。Trace ID不是唯一消息标识，Trace耗时图按所选msgId和已加载尝试展示。

Docker路径通过Nginx统一四页面，两个中台实例受健康检查管理；本地源码路径提供仅loopback的Go网关和单中台，便于调试。页面令牌与内部诊断令牌独立，浏览器不保存凭据。内置Mock及单节点中间件用于本机Demo，不代表生产高可用拓扑或容量承诺。
